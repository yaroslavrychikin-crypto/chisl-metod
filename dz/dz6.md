## Домашнее задание №1: Поиск элемента — `list` vs `set` vs `dict`

### Условие

Даны три способа проверить, есть ли число в коллекции:
1. `x in list` — линейный поиск.
2. `x in set` — поиск по хеш-таблице.
3. `x in dict` (проверка ключей) — тоже хеш-таблица, но с парами ключ-значение.

Напишите бенчмарк, который для `n = 100, 1_000, 10_000, 100_000` замеряет время **1000 проверок** в каждой из трёх коллекций. Постройте график с лог-шкалой по оси Y и сделайте вывод.

### Требования к сдаче

1. **Скрипт** `hw1_search.py`, который:
   - использует `timeit` с `repeat=5` и берёт минимум;
   - нормирует результат на одну проверку (мкс);
   - выводит таблицу: `n`, время для каждой коллекции, во сколько раз `set` и `dict` быстрее `list`;
   - строит график с тремя линиями, лог-шкалой по Y, легендой, подписями осей и сеткой (`which="both"`);
   - сохраняет график в `hw1_search.png` с `dpi=150, bbox_inches="tight"`.


### Текстовые подсказки

1. **Данные.** Для каждого `n` создайте `data_list = list(range(n))`, `data_set = set(range(n))`, `data_dict = {i: i for i in range(n)}`. Ищите число, которого **нет** в коллекции (например, `-1`) — это худший случай для `list`, и разница будет максимально наглядной.

2. **`timeit` и `globals`.** Строка `stmt` не видит ваши локальные переменные. Передайте их через `globals={"target": target, "data": data_list}`. Без этого получите `NameError`.

3. **Нормировка.** `timeit.repeat(...)` возвращает суммарное время за `number` выполнений. Разделите на `number`, потом умножьте на `1_000_000` — получите микросекунды на одну проверку.

4. **Лог-шкала.** `ax.set_yscale("log")`. Для сетки на мелких делениях — `ax.grid(True, which="both", alpha=0.2)`.

5. **Ожидаемая картина.** `set` и `dict` на лог-шкале будут почти горизонтальными (O(1)), `list` — расти с наклоном (O(n)). Если `list` не растёт — вы ищете существующий элемент, и он находится в начале.

6. **Про `dict` vs `set`.** `set` внутри устроен как `dict` без значений, поэтому асимптотика одинаковая. Разница — в константах: `dict` хранит и ключи, и значения, поэтому чуть больше памяти и микроскопически медленнее. На графике это может быть незаметно — это нормально, упомяните это в выводах.

7. **Про существующий элемент.** Если искать `target = 0`, `list` найдёт его за O(1) (он в начале), и разница с `set` исчезнет. Это важный вывод: сложность `list` — **худший случай** O(n), а не средний.

## Домашнее задание №2: Три способа создать список квадратов — время и память

### Условие

Создайте список квадратов чисел `0..N-1` тремя способами:
1. Цикл с `append`.
2. Списочное включение (list comprehension).
3. `list(map(lambda i: i*i, range(N)))`.

Для `N = 50_000, 200_000, 800_000` измерьте **время** (`timeit`) и **пиковую память** (`tracemalloc`). Постройте дашборд из двух графиков рядом: время (линии с маркерами) и память (группированные столбцы). Сделайте вывод.

### Требования к сдаче

1. **Скрипт** `hw2_squares.py`, который:
   - для каждого `N` и каждого способа замеряет время через `timeit.repeat(..., number=1, repeat=5)` и берёт `min`;
   - для каждого `N` и каждого способа замеряет пиковую память через `tracemalloc` (выполняя тот же код через `exec`);
   - строит `fig, (ax1, ax2) = plt.subplots(1, 2, figsize=(13, 5))`: на `ax1` — линии времени, на `ax2` — группированные столбцы памяти;
   - на `ax2` подписывает ось X как `N=50000`, `N=200000`, `N=800000` (а не 0, 1, 2);
   - сохраняет дашборд в `hw2_squares.png` с `dpi=150, bbox_inches="tight"`.
2. **Файл `hw2_analysis.md`** (5–7 предложений) с ответами:
   - Почему пиковая память у всех трёх способов почти одинаковая?
   - Почему list comprehension быстрее цикла с `append`?
   - Почему `map + lambda` обычно медленнее list comprehension?
   - Что изменилось бы по памяти, если бы мы создавали **генератор**, а не список?


### Текстовые подсказки

1. **Три фрагмента для `timeit`.** Подготовьте три строки: `"out = []\nfor i in range(N):\n    out.append(i*i)"`, `"out = [i*i for i in range(N)]"`, `"out = list(map(lambda i: i*i, range(N)))"`. Многострочный код в `timeit` допустим, но отступы должны быть корректными.

2. **`number=1` для времени.** Создание списка на 800 тысяч элементов — не микрооперация. Повторять её 1000 раз внутри одного замера не нужно: `number=1` достаточно, а `repeat=5` даст пять независимых замеров, из которых берётся `min`.

3. **`tracemalloc` — последовательность.** `tracemalloc.start()` → выполнить код → `current, peak = tracemalloc.get_traced_memory()` → `tracemalloc.stop()`. Вам нужен `peak` — пиковая память. Перевод в МБ: делить на `1024 * 1024`.

4. **`exec` для памяти.** `timeit` выполняет строку сам, а `tracemalloc` — нет. Выполните ту же строку через `exec(stmt, {"N": N})`. `exec` не возвращает значение, но нам нужен только факт создания списка — этого достаточно.

5. **Дашборд.** `fig, (ax1, ax2) = plt.subplots(1, 2, figsize=(13, 5))`. На `ax1` — `ax1.plot(N_values, times, "o-", label=...)` для каждого способа. На `ax2` — группированные столбцы: `x = range(len(N_values))`, `width = 0.25`, сдвиг `(i - 1) * width` для i-го способа.

6. **Подписи оси X для столбцов.** После `ax2.bar(...)`: `ax2.set_xticks(list(x))` и `ax2.set_xticklabels([f"N={N}" for N in N_values])`. Без этого на оси X будут 0, 1, 2 вместо размеров.

7. **Ожидаемая память.** Все три способа дадут **примерно одинаковую** пиковую память: результат — один и тот же список на N `int`. Промежуточные объекты (`append`-вызовы, lambda-вызовы) краткоживущие и почти не влияют на пик. Это ключевой вывод: память определяется **результатом**, а не способом его получения.

8. **Ожидаемое время.** List comprehension обычно быстрее всех: цикл на уровне C без вызовов `append`. `map + lambda` проигрывает из-за накладных расходов на вызов lambda для каждого элемента. Ручной цикл с `append` — медленнее comprehension из-за метода `append`, вызываемого N раз.

9. **Про генератор (для анализа).** Если заменить список на генератор (`(i*i for i in range(N))`), пиковая память упадёт до константы (несколько сотен байт) — элементы вычисляются по требованию. Но время `sum(gen)` будет сопоставимо с циклом, потому что генератор тоже интерпретируется поэлементно.

10. **Формулировка вывода.** В конце скрипта — `print(...)` с тремя пунктами: (а) по памяти все способы равны, потому что результат одинаковый; (б) list comprehension быстрее из-за отсутствия вызовов `append`; (в) `map + lambda` медленнее из-за накладных расходов на lambda.
